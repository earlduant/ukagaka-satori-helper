# 作れるかどうかを判断する

「〜を作りたい」と言われたときに引く。

里々は文字列を1本組み立てて返すだけで、画面・音・入力・時間を持っているのは SSP である。
できることには輪郭があり、外にあるものはどう書いても作れない。

**できないものは、仕様を詰める前に言う。**
実現できない要望の細部を聞き出しても、聞いた分だけ無駄になる。

ここにあるのは、判断するための事実と、当てはめる条件である。
依頼ごとの結論はここに無い。事実と条件から、自分で出す。

伝え方は `dialogue.md`、実装の書き方は `syntax.md`、
どこに表示を置くかは `ui_architecture.md`、確かめ方の手順は `testing.md`。

## ここに書いてあるのは、記録時点の事実である

SSP の機能は増え続ける。「できない」には賞味期限がある。
以前できなかったことが、今はできることがある。

- 仕様の説明に版の表記（`2.7.52以降` `[2.5.16]`）がある項目は、比較的新しい追加
- 「できません」と答える場面ほど、知識が古い可能性を疑う

**「無い」の断言はコストが高い。**「ある」は1件見つければ済むが、
「無い」は探し尽くさないと言えない。→ [「無い」と答える前に](#無いと答える前に)

## 原理

原理は `SKILL.md` の「里々と SSP は別のものである」にある6つ。ここには再掲しない。
個別の機能を調べる前に、まずそれで切り分ける。

この下にあるのは、原理から導けないものだけである。

特に「里々の外にあるもの」は、原理から判断しない
（→ [通知されるもの](#通知されるもの)）。SSP が橋渡ししていることがある。

## 辞書に書いたことしか喋らない

AI 搭載のマスコットとの取り違えを、最初に解く。
依頼者がまず持っている誤解で、あらゆる要望の前提になる。

- 「こういうときはこう言う」を全部あらかじめ書いておく方式
- 書いていないことは一言も喋れない
- **内容を理解する力が無い。**未知の入力に対して反応を組み立てることはできない

したがって、外から情報が取れても、それだけでは何も喋れない。

| 要望 | 取れるもの | それでも書くもの |
|---|---|---|
| 天気で会話を変えて | 天気 | 晴れ・雨・雪それぞれのセリフ |
| 名前を呼んで | ユーザー名 | 名前を埋める文型 |
| 再生中の曲に反応して | 曲名・アーティスト名 | キーワードごとのセリフ |
| 気の利いたことを言って | ─ | **何が気の利いたことかを、書く人が決める** |

「タイトルを見て感想を言う」形の要望は、
想定される入力と、それに対するセリフを1つずつ用意する作業になる。
外れたとき用の一言を置いておくと自然に見える。

## 作れるものの条件

**4つとも満たせば作れる。1つでも外れると破綻する。**

1. 状態が離散的 ── 場面が有限個で、飛び飛びに切り替わる
2. 入力が離散的 ── クリックやキー。連続的な操作（ドラッグ、同時押し）を使わない
3. 時間が進まない ── 操作されるまで世界は止まっていてよい
4. 画面が切り替わる ── 連続的に変化しない

当てはめた例。一覧ではない。形式名が同じでも中身は依頼ごとに違う。
**この表を引き写して答えない。**条件のどれが外れるかを、依頼の中身に当てて出す。

| 形式 | 外れる条件 |
|---|---|
| ノベルゲーム／クイズ／すごろく／育成もの | ─ |
| 脱出ゲーム／謎解き／クリックアドベンチャー | ─ |
| キー操作でキャラを歩かせる | 規模次第。障害物の判定を辞書側で持つ（下記） |
| ローグライク | 規模次第。盤面を描き直す量 |
| リズムゲーム／スロットの目押し | 2。止めた位置を辞書が知らない（下記） |
| アクション／シューティング／タワーディフェンス | 2・3・4 |

### キー操作によるキャラ移動

`OnKeyPress` で入力を受け、定義済みアニメーションで歩かせ、位置をずらせば動く。

難しいのは障害物の判定。当たり判定はクリックを受けるためのもので、
物体同士がぶつかったかを返さない（→ [当たり判定](#当たり判定)）。
地形を辞書側の変数で持ち、移動のたびに「次の位置は通れるか」を自分で計算する。

部屋1つ程度なら現実的。広いマップ、複雑な地形、動く敵が加わると、
持つ情報も計算も急に増える。局所的に可能と伝える。

### 止める位置で決まるもの

リズムゲーム、スロットの目押し。

見た目は作れる。流れる音符も回るリールも、定義済みアニメーションとして用意でき、
SSP が滑らかに描く。

**判定が成立しない。**

- 再生中のアニメーションが、いまどのコマかを辞書は知らない。
  止めても、どの絵で止まったかが分からない
- 1コマごとに辞書を呼べば分かるが、往復に十数ミリ秒かかる。
  速い動きには追いつかない
- 入力から辞書が呼ばれて返るまでの時間も、一定でない

結果を先に決めておけば、その通りに止まる演出は作れる。
ただし、利用者がいつ押したかは結果に影響しない。

### 画像を使うゲーム

| | |
|---|---|
| 画像を出す・切り替える | できる |
| 画像を動かす | できる。ただし3通りあり、コストが違う（→ [動きの作り方](#動きの作り方)） |
| 画像を変形する | できない |
| 画像を大量に並べる | **数の問題。**先に規模を聞く（→ [規模で破綻する](#規模で破綻する)） |

**「動かせない」と答えない。**動かし方を選べば作れる。
破綻するのは、動かすことではなく数である。

## 規模で破綻する

二値で答えない依頼がある。規模によって作れたり作れなかったりするものは、
**先に規模を聞く。**

### 分解が先

規模を見積もる前に、分けられないかを見る。

| 要件 | 逃げ道 |
|---|---|
| シェルに出す | バルーンなら `\_b` でファイル名を組み立てられる。事前の定義が要らない |
| 動かす | 移動が要らないなら、定義済みアニメーションで切り替える |
| 辞書が並べる | 利用者に並べさせれば、比較は起きない（→ `ui_architecture.md`「掴んで並べ替える」） |
| 種類が増える | 更新で絵と定義を足せる。作り切りではない |

辞書が全部やる前提で見積もらない。
分解して残ったものだけが、規模の問題になる。

### 何が増えるのか

| | |
|---|---|
| 出力の量 | 繰り返しの回数に比例して、返す文字列が伸びる。画面全体を組み直すため |
| 計算の量 | 並べ替えの比較回数は、要素数の2乗になる。里々に並べ替えは無く、自分で書く |
| 画面の描き直し | バルーンは一部だけ描き替えられない（→ [画面の更新](#画面の更新)）。状態が変わるたびに全部 |
| 持つ変数 | 連番の変数か単語群で持つ。件数ぶんの読み書きが毎回走る |
| ウィンドウの数 | 1つずつ別に動かすなら、その数だけ要る。推奨は2〜3個（→ [ウィンドウ](#ウィンドウ)） |

### 閾値を持たない

**「○個以上は重い」という数値を知識として持たない。**
マシン性能・SSP の版・バルーンで変わり、古くなり、
示すと「それ未満なら安全」という誤解を生む。

測れる。テスターで実際に動かす（→ `testing.md`）。
持つのは「規模が増えると破綻する」という性質と、小さく作って確かめる進め方だけ。

## 描画

**SSP は用意された画像を出すことしかできない。実行時に画像を生成・加工しない。**
例外は、位置の移動とアルファ値の操作。

| | 可否 | |
|---|---|---|
| どの絵を出すかの指定、定義済みアニメーションの再生 | できる | ─ |
| 爆発などのエフェクト | できる | フレーム画像を用意して差し替える |
| 位置の移動 | できる | 例外 |
| 透明度の変更 | できる | 例外 |
| 任意角度の回転・拡大縮小 | できない | 角度と倍率は無限。事前に用意できない |
| 絵の動的な合成 | できない | 組み合わせが無限 |
| キャラクターの絵に文字を表示 | できない | 文字列が無限。事前に画像化できない |

文字が出せるのは吹き出しの中だけ。絵の上に出したいなら、
文字を含めた画像を用意して重ねる。

仕様を引くと「サーフェス上にテキストを表示する」（`\![anim,add,text,x,y,…]`）が
出てくることがあるが、**CROW 専用で SSP では動かない。**

**「合成できない」と「移動できない」は別。**位置は動かせるので、
キャラクターを歩かせるような表現は成立する。

絵そのものは作れない。定義は書けるが、画像は用意してもらう。
できあがりが正しく見えているかも確認できない（→ [確かめられる範囲](#確かめられる範囲)）。

## 動きの作り方

3通りあり、コストがまったく違う。

| | 辞書の関与 | |
|---|---|---|
| 定義済みアニメーションの再生 | 起動時だけ。再生中は呼ばれない | SSP が描くので滑らか |
| 動き全体を1本の列に組み立てて渡す | 最初の1回だけ | 位置を自由に決められる（→ `ui_architecture.md`「時間で動かす」） |
| 1フレームずつ辞書から動かす | 動かすたびに呼ばれる | **往復が挟まるので、頻度を上げると破綻する** |

**「絵を動かす＝辞書が毎回呼ばれる」ではない。**
連続的で滑らかな動きは、シェル側にアニメーションとして定義すれば実現できる。

定義済みのほうには制約がある。

- 動きが固定される。定義したとおりにしか動かない
- 再生中の現在位置を、辞書が知らない。動かしているのは SSP なので、
  座標を取得する手段が無い

バルーンは、全体を作り直して出し直す。

シェルは別。アニメーションは個別に動かせるので、変わったところだけ呼べばよい
（→ [動きの作り方](#動きの作り方)）。

## 実行の途中には手を出せない

実行の最中に別のこと（クリックなど）が起きると、SSP は辞書を呼ぶ。
そこで何を返しても、道は3つしかない。

| 返すもの | 実行中のもの | 返したものが出るのは |
|---|---|---|
| 204 | そのまま続く | 出ない |
| 200 | 破棄される | すぐ。ただし先頭から |
| 200（先頭に `\C`） | 最後まで出し切る | それが終わってから |

```
＊OnMouseDoubleClick
：こんにちは。

＠OnKeyPress
\Cなんですか？
```

```
「こんにちは。」を出している最中、「こん」まで出たところでキーが押された

  ＠OnKeyPress が無い   204。「こんにちは。」がそのまま最後まで出る。反応は起きない
  \C を書かない         バルーンの文字が消え、「なんですか？」が1文字目から出る
  \C を書く             「こんにちは。」を最後まで出してから「なんですか？」が続く
```

`\C` を本当の先頭に置くため `＠` で受けている。
`＊` は先頭にサーフェス指定が自動で入るので、そこに置けない（→ `display.md`）。

消すか、待つか、何もしないかである。

待つ時間は作者に決められない。残りの文字数と、利用者が決めた文字送りの速さで決まる。

**どこまで実行されたかを知る手段も無い。**
「喋っている最中か」「選択肢を出しているか」といったおおまかな状態は受け取れるが、
何文字目まで出たかは分からない。しかもその値はイベントが届いた時点のもので、
実行が進んでも変わらない。繰り返し見に行って進み具合を追うこともできない。

ただし、通過点を仕込むことはできる。
`\![embed,イベント名]` を列の途中に置くと、そこに到達した時点で辞書が呼ばれる。
問い合わせることはできないが、決めた場所を通ったことは分かる
（→ `ui_architecture.md`「時間で動かす」）。

割り込ませない書き方は `display.md`、状態を見て抑える書き方は `internals.md`。

里々Wiki に「talking 中に `\C` を頭に付けたトークを割り込ませると、
現在喋っているトークの末尾に追記できる」という記述がある。
**追記されるのは、実行中のものが終わってからである。**

## キー入力

キーが押されたことを受け取れる。

| 一緒に届くもの | |
|---|---|
| 押されたキー | 文字と、仮想キーコードの両方 |
| 押しっぱなしの回数 | 押し続けている間、同じイベントが繰り返し届く。1から数える |
| 修飾キー | `ctrl,alt` のようにカンマ区切りで列挙される |

**離したことは通知されない。**押している間は届き続け、離すと来なくなるだけである。

押した長さは、時間には直せない。
繰り返しの間隔は利用者の OS 設定で決まり、最初の1回と2回目の間だけ大きく空く。
「離した」を捉えるなら、秒ごとのイベントで「最後の入力から時間が経った」を見る。
そこで得られる粒度は秒単位になる。

押しっぱなしの間は、短い間隔で何度も呼ばれる。
1回ごとの処理が重いと、間に合わなくなる（→ [規模で破綻する](#規模で破綻する)）。

**キー同士の同時押しは、そのままでは分からない。**イベントは1キーずつ届く。
上の修飾キーは一緒に来るが、通常のキーを2つ同時に押したことは SSP が教えてくれない。

## 当たり判定

クリックを受ける領域を、絵の上に決められる。

| | |
|---|---|
| サーフェスに付けた判定 | 動かない |
| アニメーションに付けた判定 | `\![anim,offset]` で動かすと、判定も一緒に動く |

動く的をクリックさせることはできる（→ `ui_architecture.md`「時間で動かす」）。

**動く物体同士がぶつかったかを判定する仕組みは無い。**
必要なら、位置を辞書側の変数で持って自分で計算する（→ [作れるものの条件](#作れるものの条件)）。

## ドラッグ

**取れない。**画面上でのドラッグはキャラクターの移動として扱われる。
吹き出しに絵を並べても、それを掴んで動かすことはできない。

掴めるようにする唯一の方法は、動かしたいものを別キャラクターとして表示すること。
ウィンドウが増えるので現実的な範囲は狭い（→ [ウィンドウ](#ウィンドウ)）。

代案はクリックで選ぶ形。一覧を出して選ぶ、対象を選んでから操作を選ぶ。
数が増えても破綻しない。

**目的と手段を分ける。**「ドラッグで着せ替えたい」は手段だけが不可で、
着せ替え自体は実現できる（→ [着せ替え](#着せ替え)）。

## ウィンドウ

- 別キャラクターとして表示すると、利用者がマウスで掴んで動かせる
- 重なりを検知できる
- 一体化・分離ができるので、移動の表現に使える
- 束ねて扱うなら、公式の推奨は2〜3個。
  それ以上は、時々おかしくなることがある（→ `ui_architecture.md`「掴んで並べ替える」）

## 背景

**伺かに背景という仕組みは無い。**
ただし背景の絵を1体のキャラクターとして作り、その手前に本来のキャラクターを立たせれば、
同じ見た目になる。

- 場面転換は、その絵の切り替え
- 背景の一部に触り判定を付けられる
- 立ち絵の入れ替えも同じく切り替え

背景を前提とする形式（ノベルゲーム、アドベンチャー）を求められたら、この構成を出す。
組み立て方は `ui_architecture.md`「重ねて見せる」。

## 着せ替え

SSP の標準機能。シェル側で定義し、メニューから切り替えられる。
辞書からも切り替えられる。

利用者の着せ替えメニューに載せるかどうかは分けられるので、
見せる着せ替えと、機能のための着せ替えを分けられる（→ `ui_architecture.md`）。

## 音声

| | |
|---|---|
| 鳴らす・止める | できる |
| 再生位置（今何秒目か） | **取得できない** |

したがって「曲に合わせる」ことはできない。
再生開始と同時に、時間を決め打ちしてイベントを起こす形になる。

ズレの原因は、曲の読み込み時間、途中で止めた場合、他の処理との競合。
ズレは蓄積しないが、開始時点のズレは最後まで残る。

数秒のズレが問題にならない用途（サビで場面転換など）なら実用的。
厳密に合わせたいなら、曲を区切って順に鳴らす。

---

## 時間

| | |
|---|---|
| 秒ごとのイベント | 1秒間隔。これが基本の刻み |
| ミリ秒指定のイベント | 起こせる。繰り返しの指定もできる |

**短い間隔で使うと、作りが破綻する。**

- 返事を組み立てている最中に、次の呼び出しが来る
- 利用者の操作と競合する
- 辞書の呼び出しは同期なので、処理中は SSP が待つ

動くには動くが、狙った順序では動かない状態になりやすい。

## バルーン

文字と画像を並べて、クリックさせられる。一覧・メニュー・図鑑・数値の表示はここで作る。

**大きさもフォントも利用者が決める。**固定の行数や文字数を前提にした表示を組まない。

書き方は `display.md`、複数のデータを並べるなら `patterns.md`、
シェルとの使い分けは `ui_architecture.md`。

## 外に触れられない

方向によって違う。

| | |
|---|---|
| 辞書から読みに行く | できない |
| SSP が通知してくる | できる。範囲は想像より広い（→ [通知されるもの](#通知されるもの)） |

読みに行けないもの。

- ファイルの中身を読む／書く手段が無い
- 通信機能が無い
- **SSP の汎用 HTTP 機能を使っても、結果はファイルに書き出されるので受け取れない**

ただし送信は成立する。外部へ送ることはでき、
HTTP のステータスコードがイベントで返るので成否は判定できる。
アンケートの回答収集のように、片道で完結する用途なら実現できる。
受け取った内容を使う設計にはできない。

### 渡されたものには反応できる

- ドロップされたファイルのパスを受け取れる
- 拡張子で分岐して反応を変える、といった処理は普通に書ける

**「勝手に見る」と「渡してもらう」を分けて答える。**
前者は不可、後者は可能。
目的が「パソコンの中身に反応してほしい」なら、後者で満たせることが多い。

## 通知されるもの

SSP が橋渡ししている可能性が常にある。

- SSP が用意した機能（ネットワーク更新、ヘッドライン、メールチェック、時刻合わせ）
- 再生中の曲のタイトル・アーティスト名（`OnMusicPlayEx` [2.7.55]）
- 動画の情報（`OnVideoPlayEx` [2.7.59]）。ブラウザでの再生も、ここに来る

### 里々とベースウェア以外の媒体は、仕様を引いてから答える

ブラウザ、音楽プレイヤー、動画プレイヤー、他のアプリ、OS の状態 ──
**「里々の外にあるもの」への要望は、原理から「できない」と判断せず、
必ず SHIORI イベントの仕様を引いて、受け取れるものが無いかを探す。**

上の2つはどちらも新しい機能で、原理からは絶対に導けない。

通知されても、喋る内容は書く（→ [辞書に書いたことしか喋らない](#辞書に書いたことしか喋らない)）。

---

## 里々に無い機能

**無いことだけを見て「できない」と判断しない。**代わりの手段まで見る。
対応表は `syntax.md`「無い機能と、その代わり」。

| | |
|---|---|
| 配列・連想配列・ローカル変数 | 無い。引数の分割、単語群、変数名の組み立てで代用する（→ `patterns.md`「データを持つ」） |
| 並べ替え | 無い。自分で書く（→ [規模で破綻する](#規模で破綻する)） |
| 正規表現 | 無い |
| ファイルの読み書き | ほぼ無い |
| 小数の計算 | **できる。**ただし既定の計算は整数に丸められる |
| 大きな数 | 32bit の整数。秒やミリ秒に直すと、思ったより早く桁があふれる |

変数はすべてグローバルで、終了時に保存される。
「覚えさせる」系の要望は、これで素直に実現できる。

里々単体でできないことを外部 DLL に渡す手段はあるが、
**このスキルは扱わない。**配布物に DLL の同梱が必要になる。

---

## やるべきでないこと

技術的な可否とは別に、やらないほうがよいと伝える。

外部 DLL を書けばファイルの読み書きは技術的に可能になるが、
**ブラウザの履歴やデスクトップの内容を、同意なく読むのはやるべきでない。**

- 使う人にとって不安な振る舞いになる
- ウイルス対策ソフトに引っかかる可能性がある
- 配布物としての信頼を損なう

## 確かめられる範囲

「作れるか」と「AI に頼むべきか」は別の問いである。

境界そのものは `SKILL.md` の原理4にある。ここにあるのは、それを依頼に当てはめる形である。

| | 内容 | |
|---|---|---|
| 1. 辞書の記法 | 括弧、引数の個数、行頭記号 | 確かめられる |
| 2. 返る文字列 | 分岐、変数の値、タグの並び | 確かめられる |
| 3. 画面の見え方 | 位置、重なり、表情が合っているか | 確かめられない |
| 4. 体験の質 | 面白いか、テンポが良いか | 確かめられない |

3 が本質の仕事は、書いても確認できない部分が多い。

**「作れます」と答えるときは、どこまで自分で確かめられるかを併せて伝える。**
手順は `testing.md`、伝え方は `dialogue.md`。

**既存の辞書に無いタグを使った場合、SSP がそれを実装しているかは確かめられない。**
辞書は正しい文字列を返し、テスターも通る。

## 「無い」と答える前に

「できません」と答える場面ほど、調査を厚くする。

引いて 0件だったときは、存在しないのではなく、引き方が違うと考える。
**複合語は分解し、最低3方向から引く。**

1. 日本語の説明に使われそうな語（文字／テキスト／表示）
2. タグ名になりそうな英語（text／anim／draw）
3. 上位の概念（サーフェス／アニメーション／バルーン）

MCP で見つからなければ、Web の情報も取る。
MCP は索引なので、元のページにある情報が落ちていることがある。

**知らないことを「できない」に言い換えない。**
語調の分け方は `dialogue.md`。
