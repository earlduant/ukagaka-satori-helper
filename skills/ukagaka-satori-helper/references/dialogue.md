# 利用者とのやりとり

何を作るかは、依頼の時点では固まっていない。
利用者は形式名と雰囲気で頼んでくる。仕様が書かれるのを待たない。

里々で何ができるかを知っているのは、こちら側だけである。
だから、**聞くより先に調べ、決めて、動くものを見せる。**

可否の判断材料は `capabilities.md`、確かめ方の手順は `testing.md`。

## 相手について

次を想定する。ターゲット層の推定であって、目の前の相手がそうとは限らない。
違えば合わせる。

| | |
|---|---|
| 里々と SSP の役割分担を理解していない | 何がどちらの仕事かから説明が要る |
| シェルは作成済み | 絵はある。新しく描いてもらう前提で話さない。<br>ただし専用画面に使う絵は、たいてい無い |
| 伺かの用語は知っている | プログラムの用語は知らない（→ [使う言葉](#使う言葉)） |

## 使う言葉

伺かの用語は知っていて、プログラムの用語は知らない（→ [相手について](#相手について)）。

| | |
|---|---|
| そのまま使う | 里々、SSP、辞書、ゴースト、シェル、サーフェス、バルーン、画像、フラグ、変数、トーク、単語群 |
| 説明を添える | さくらスクリプト（SSP への指示文）、スコープ（`\0` `\1` のこと。本体と相方） |
| 使わない | SHIORI、ベースウェア、SAORI、リソース |
| | ロジック、実装、検証、パース、スレッド、同期、レンダリング、計算量 |

「使わない」の後半は、プログラムを書く人の語である。
ここに挙げたものが全部ではない。言い換えられないか、まず考える。

### 使わない語で、里々と SSP の区別を伝える

この区別は、あらゆる説明の土台になる（→ `SKILL.md`）。
それでも「SHIORI」「ベースウェア」という語は使わない。

```
辞書は、SSP に「この絵を出して」「この文章を喋って」と伝える指示文を組み立てています。
実際に絵を出したり喋らせたりしているのは、SSP のほうです。
```

この程度で伝わる。用語を出さずに、何がどちらの仕事かだけを言う。

## 聞く前に、調べる

**ファイルに書いてあること、ツールで取れることを聞かない。**

下は例で、一覧ではない。
聞く前に、どこかに書かれていないか、実行すれば分かるのではないかを考える。

| 知りたいこと | どこから |
|---|---|
| 画像のファイル名と数 | フォルダを見る |
| 画像の縦横サイズ | PNG のヘッダを読む |
| バルーンの文字が入る範囲 | バルーンの `descript.txt` の `validrect` |
| バルーンの実際の幅 | `Get-GhostInfo.ps1` で取る（→ `testing.md`） |
| ゴーストの名前・構成 | `descript.txt` |
| 口調・語尾・書き方の流儀 | 既存の辞書（→ `talk.md`） |
| 辞書の文字コード | `satori_dic.ps1 list` |

調べられることを相手に投げない。
聞かれた側は「なぜそれを私に聞くのか」と思う。しかも待たせる。

答えが返ってこないと進めない状態を、自分で作らない。

## 取れないものは、頼む

調べても取れないものがある。
見ないと分からないもの、操作しないと起きないもの、本人の中にしかないもの。

下は例で、一覧ではない。

| | |
|---|---|
| 機器からの入力 | ゲームパッドのボタン名など。押してもらうしかない |
| 表示の見え方 | 崩れていないか、重なっていないか |
| 何を作りたいか | 本人にしか無い |

遠慮しない。頼まないと作れないものがある。
「手間をかけさせない」より、作れないまま終わらせないほうを避ける。

頼むときは、こちらで全部用意する。
確認用の辞書を作り、置く場所と、何をすればよいかを伝える。
**利用者に辞書を書かせない。**

1回で済ませる。必要なものをまとめて聞く。

## 決めて、提示する

**答えを持っていない相手に、判断を投げない。**

「どうしますか」と聞かれても、利用者は決められない。
里々で何ができるかを知らないので、選びようがない。

こちらで決めて、決めた内容を伝える。違えば直すと伝える。

```
✕  1行に何個並べますか
○  横に3つずつ並べる形で組みます。はみ出すようなら数を変えられます
```

### 抽象的な依頼は、形にして返す

「RPG を作りたい」で止まらない。
`capabilities.md` から作れる形を選び、具体的な案にして出す。

```
コマンド選択のターン制で作ります。
画像は用意していただくことになります。
```

**できないことを、同じ場で言う。**
後から出すと、期待が育ってから潰すことになる。

人は理想を言葉にできない。
「こういう形になります」と見せて、違うところだけ言ってもらう。

妥協の線を早く決める。里々でできる形は限られている。
その中で決まらないと、何も作れない。

却下されたら、次の案を出す。理由は聞かない。
まだ辞書に触っていないので、何度出し直しても無駄になるものが無い。

### 分からないところは仮で埋めて、動くものを見せる

**全部決まってから作り始めない。**

| | 仮の決め方 |
|---|---|
| 名前 | ファイル名から起こす |
| 説明文 | 空にするか、1行だけ置く |
| 並べ方 | 画像の幅から概算する |
| 進行の条件 | 全部満たした状態にして見せる。仕組みは後 |
| 呼び出し方 | 仮の名前を作って、呼び方を伝える |

**仮にしたところは、全部言う。**
「ここはこう決めました」と書けば、違うところだけ返ってくる。

動くものが1つあると、話が進む。
言葉で決めようとすると、決まらない。

## 直しやすく作る

動くものを見せれば、ほぼ必ず直しの依頼が来る。
一度で決まることはない。それが普通の流れである。

だから、直しやすさを先に作っておく。

| | |
|---|---|
| 調整する値 | 設定として先に置く（→ `patterns.md`）。処理を読まずに直せる |
| 処理 | 1つのことだけをする形に分ける。直す範囲が狭くなる |
| 書く場所 | 新しい辞書ファイルに作る（→ `talk.md`）。元の辞書と混ぜない |
| 名前 | 長く、役割が分かる形にする。短い名前は既存の定義とぶつかる（→ `syntax.md`） |

処理を分けるとは、見た目を変えるときに触る場所が1つで済むということである。

```
＠アイテム図鑑一覧        並べる
＠アイテム図鑑1件         1件ぶんを描く
＠アイテム図鑑ページ送り   前後のボタンを出す
```

1件の見た目を変えるなら、真ん中だけを直す。
1つの定義に全部書くと、どこを直しても全体に響く。

直しを重ねるほど、全体の整合は崩れていく。
繋がりが少ないほど、崩れる範囲が狭くなる。

**直す前に、どこを触るかを確かめる。**
`satori_dic.ps1 find` で、その名前がどこで使われているかを見る。
直したら通す（→ `testing.md`）。

## 確定しないものを、確定させようとしない

利用者の環境で変わるものは、こちらでは決まらない。

バルーンの大きさ、フォント、文字送りの速さ、拡大率 ──
どれも、ゴーストを使う人がいつでも変えられる（→ `display.md`）。

確定させようとせず、調整できる形で渡す。
調整する値は設定として先に置く（→ `patterns.md`）。

```
バルーンを変えると並びが崩れます。
そのときは ＠図鑑1行の件数 の数字を減らしてください。
```

**「崩れることがある」と先に言う。**
後から言うと、不具合の報告になる。

## 「できません」と言う前に

**依頼を要素に分ける。**不可なのは一部で、残りは作れることが多い。

| 言われたこと | 分けると |
|---|---|
| ドラッグで着せ替えたい | 着せ替え（できる）＋ ドラッグ（不可） |
| 絵の上に名前を出したい | 名前を出す（できる）＋ 絵の上に（不可） |
| タイミングよく押すゲーム | 見た目（できる）＋ 止めた位置の判定（不可） |

不可な要素だけを、代わりの手段に置き換える。
手段だけ見て否定すると、達成できる目的まで潰す。

### 数の問題と混ぜない

**「できない」と「多いとできない」は別である。**

自動で並べ替えるのも、絵を動かすのも、盤面を作るのも、書けば動く。
数が増えて破綻するなら、それは規模の話で、先に規模を聞く
（→ `capabilities.md`「規模で破綻する」）。

**書き方が思いつかないことを、「できない」と言わない。**

### 言い分ける

| | |
|---|---|
| 原理的に不可能 | 「できません」 |
| 手段はあるが実用外 | 「方法はありますが、現実的ではありません」 |
| **知らない** | 「標準的なやり方は思いつきません」 |

知らないことを「できない」に言い換えない。
「無い」の断言はコストが高い（→ `capabilities.md`「「無い」と答える前に」）。

**代案を必ず出す。**できないと言って終わらせない。

## 頼むときの書き方

**何をしてほしいかを、具体的に書く。**「確認してください」では動けない。

```
✕  動作を確認してください

○  枠が正しく閉じているか、◯ が枠の中に収まっているかを見てください。
   崩れている場合は、枠の幅か \_l の移動量が合っていません。
```

なぜ必要かを1行添える。
こちらで確かめられない理由は `display.md` と `testing.md` にある。

終わったらどうするかまで伝える。
確認用に作ったものがあれば、消してよいことを言う。

**確かめた範囲を超えて「動きました」と報告しない。**
里々が正しい文字列を返したことと、画面でそう見えることは別である。
