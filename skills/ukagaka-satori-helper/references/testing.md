# 確かめ方

SSP を起動せずに `satori.dll` を直接動かし、イベントを送って応答を見る。

里々はエラーを出さない。**動かさずに「書けた」と報告しない。**

**辞書に触れたら通す。**
要らないのは、`talk.md` の手順でセリフを書いただけのときに限る。

記法は `syntax.md`。里々が肩代わりしている挙動は `internals.md`。

## 5本の役割

`scripts\` にある。どれも事前のビルドは要らない。

| | 何をするか | 何を見つけるか |
|---|---|---|
| `satori_runner.ps1` | イベントを送って応答を取る | 里々自身が報告するエラー |
| `satori_lint.ps1` | 辞書を静的に検査する | 里々もテスターも何も言わない誤り |
| `satori_script.ps1` | 応答したさくらスクリプトを検査する | 壊れたタグ、閉じられていない範囲 |
| `satori_log.ps1` | 里々の内部ログに問い合わせる | 応答が期待と違うときの原因 |
| `Get-GhostInfo.ps1` | 起動中のSSPに問い合わせる | バルーンサイズなどの実行時環境の値 |

`satori_runner.ps1` を「テスター」と呼ぶ。他のファイルでもこの呼び方を使う。

`satori_*.ps1` の引数はすべて必須。省略できるものは無い。

## 順序

```
辞書を書く
  → satori_runner    里々が報告するエラーを潰す
  → satori_lint      里々が言わないものを見る
  → satori_script    返ってきたスクリプトを検査する
  → satori_log       応答が期待と違うとき、原因を辿る
```

**`satori_lint` はテスターでエラーが無くなってから通す。**
里々がエラーを出している状態の辞書を検査しても、報告が噛み合わない。

`satori_log` は常用しない。応答が期待どおりなら引かない。

## 動かす前に

本番のゴーストは書き換わらない。`satori_runner` が作業フォルダへコピーして、
そこで動かす。里々が `satori_savedata.txt` を書くのもコピーの側。

コピーされるのは辞書と設定だけ。`satori.dll` `satori_bootconf.txt`
`satori_conf.txt` `replace.txt` `replace_after.txt` と、`dic*.txt` と `saori\`。
`dic*.txt` はサブフォルダも含めて集め、階層のままコピーする。
画像・音・フォントは里々が読まないので持っていかない。

**`ghost\master` の外は持っていかない。**
`＄辞書フォルダ` がそこを指していると、辞書が空になり `204` が返る。

32bit かどうかは気にしない。`satori.dll` は 32bit だが、
`satori_runner` が 64bit で起動された場合は自分で 32bit の PowerShell へ渡し直す。

作業フォルダは `SKILL.md` の「作業フォルダ」。4本とも同じものを渡してよい。

| 作られるもの | |
|---|---|
| `<作業フォルダ>\satori_runner\` | コピーされたゴースト。毎回消してから作り直される |
| `<作業フォルダ>\satori_runner\internal.log` | 里々の内部ログ。常に出る |

## seq.txt

送るイベントを並べたファイル。UTF-8 で書く。

```
[イベント名]
Reference0: 値
Reference1: 値

[別のイベント名]
```

- `[イベント名]` に続く行が、そのまま SHIORI ヘッダになる
- `#` で始まる行は無視される
- 同じイベントを何度書いてもよい。`load` から `unload` まで同じプロセスなので、
  変数は保持される。連続する動作はここに並べて書く

Reference の要否はイベントごとに違う。SHIORI イベントの仕様を引く。
分からないまま埋めない。

## 手順

`OnBoot` を例に、4本を一通り通す。

1. seq.txt を作る

```
[OnBoot]
Reference0: master
```

2. テスターに通す

```
powershell -ExecutionPolicy Bypass -File scripts\satori_runner.ps1 <seq.txt> <ghost/master> <作業フォルダ> "" > runner_out.txt
```

第4引数は持っていくセーブデータのパス。`""` なら初期状態から始まる。
標準出力はファイルへ落とす。次の検査がそれを読む。

3. 辞書を静的に検査する

```
powershell -ExecutionPolicy Bypass -File scripts\satori_lint.ps1 <ghost/master>
```

本番のパスを渡す。読むだけで書き換えない。
渡すのは本番なので、報告されるファイル名と行番号も本番のもの。修正するのは本番。

4. 応答したスクリプトを検査する

```
powershell -ExecutionPolicy Bypass -File scripts\satori_script.ps1 runner_out.txt <作業フォルダ>
```

5. 原因を辿る（必要なときだけ）

```
powershell -ExecutionPolicy Bypass -File scripts\satori_log.ps1 <作業フォルダ>\satori_runner\internal.log <作業フォルダ> problems ""
```

`problems` で里々が見つけられなかったものが出る。まずこれを引く。
イベント名で区間を見るなら `event <イベント名>`、変数を追うなら `trace <変数名>`。

## 応答の読み方

```
========== OnBoot ==========
SHIORI/3.0 200 OK
Value: \0\s[0]\1\s[10]\0こんにちは。\e
Charset: Shift_JIS

内部ログ: <作業フォルダ>\satori_runner\internal.log (XX 行)
```

**応答の全文を読まない。**1画面ぶんの UI はタグが数百個並んだ1行になる。
壊れていないかは `satori_script` が見る。

本文そのものは辞書にある。応答で見るのは、
どれが選ばれたか・変数や単語群が展開されたか・意図した位置にタグが入ったか。
本文を読み直すために応答を使わない。

標準出力はファイルへ落とし、`Value:` の行だけを取り出す。

```powershell
(Get-Content runner_out.txt -Encoding UTF8) | Where-Object { $_ -like "Value:*" }
```

どのトークが選ばれたかを見るなら、辞書に書いた語で絞る。

```powershell
(Get-Content runner_out.txt -Encoding UTF8) | Where-Object { $_ -match "探したい語" }
```

| | |
|---|---|
| `200 OK` | 応答が返った |
| `204 No Content` | 応答が無い。原因は2つある（下記） |
| 応答に里々のエラー文が混ざる | 引数の個数、計算不能な式など。里々が場所まで報告する |

**`204` の原因は2つあり、応答だけでは区別できない。**

| | 内部ログに出るもの |
|---|---|
| イベントが未定義（正常） | `--- Operation ---` の後が空 |
| `＞` の飛び先が無い（異常） | `not matched.` と `not found.` |

`satori_log` の `problems` を引く。

**出力が途中で切れていたら、閉じていない `[` を疑う。**
さくらスクリプトの `[` が閉じていないと、里々がバッファの外を読む。
プロセスごと落ちて応答が返らないこともある。実行のたびに結果が変わる。

**これはテスターの側で起きる現象で、SSP では発生しない。**
利用者に辞書の誤りとして報告しない。`[` を直せば起きなくなる。他に調べることはない。

### `return:` と `Value=` の差分

内部ログの `return:` は里々が組み立てた文字列、`Value=` は SSP へ返した文字列。
この差が、里々が最後に行う加工にあたる。

```
return:  \1\0起動しました。…です。\n
Value=   \1\s[10]\0起動しました。…です。\e
```

サーフェスの挿入、末尾改行の除去、`\e` の付加、`replace_after.txt` の置換、
`\q[]` への ID 埋め込みがここで起きる（→ `internals.md`）。

書いた覚えのないものが出ていたら、この差分を見る。

### 内部ログに出ないイベント

`OnMouseMove` と `OnTranslate` は里々が送信しない。
なで反応と `OnTranslate` の処理は、内部ログから追えない。
応答そのものは通常どおり取得できる。

## 状態を作る

進行度や設定によって出るものが変わる辞書は、状態を作らないと確かめられない。
手段は2つある。

seq.txt に並べる。変数を変えるイベントを先に送る。
同じプロセスで動くので、そのまま次のイベントに引き継がれる。

セーブデータを渡す。第4引数に `satori_savedata.txt` のパスを渡す。

| 渡すもの | どこから始まるか |
|---|---|
| `""` | 初期状態 |
| 本番の `satori_savedata.txt` | 利用者の進行状況 |

再現性が要るなら `""` を渡す。本番の進行状況を使うと、
同じ辞書でも利用者の状態によって結果が変わる。

## 利用者の側に残るもの

利用者が触った結果は、2か所に分かれて保存される。

| | 何が入るか | どこ |
|---|---|---|
| `satori_savedata.txt` | 里々の変数。辞書が作ったもの | `ghost\master` の直下 |
| `profile\` | SSP が覚えている位置と選択 | `ghost\master\profile`<br>`shell\<シェル名>\profile` |

`profile\` に入るのは、キャラクターの位置、動かしたバルーンのずれ、選んでいるバルーンとシェル、
入力ボックスの位置など。どれも辞書からは書けない。

### profile を消すと初期状態に戻る

初回起動を試すときに使う。消すと `FirstBoot` も消えるので、次の起動が初回の扱いになる。

位置のずれを直すときにも使える。
利用者が動かしたバルーンのずれは、ここに残っている（→ `ui_architecture.md`「重ねて見せる」）。

ただし、位置以外も戻る。

| | |
|---|---|
| 戻るもの | 位置、選んでいるバルーンとシェル、初回起動の扱い |
| **戻らないもの** | 里々の変数。`satori_savedata.txt` は profile の外にある |

**利用者に消してもらう操作なので、何が戻るかを伝える。**
「位置が直ります」とだけ言うと、選んだバルーンが変わって驚かれる。

## ランダムトークを呼ぶ

`OnTalk` を送ると、その場で1本返る。喋り間隔を待たない。

```
[OnTalk]
[OnTalk]
[OnTalk]
```

呼ばれるのは「＊」だけの、名前のない文。里々は名前のない文を特別扱いする。
`＊OnTalk` を辞書に書いていなくても呼べる。書いてあればそれを経由する。

名前の付いたトークは `OnTalk` では出てこない。
「＊」が共通処理だけを持ち、そこから別名のトークを呼んでいる辞書がある。

```
＊
：（call、ウェイト挿入、トーク）

＊トーク
：（本体はこちら）
```

トークが何本あるかは、「＊」の数ではなく、そこから呼ばれている先を数える。

`＄文「＊」の重複回避` が有効なら、一巡するまで同じトークは返らない。
本数ぶん送れば、全部を1回ずつ見られる。
採用条件の付いたトークは、条件を満たす状態を作らないと出てこない。
→ [状態を作る](#状態を作る)

`（Ｒ０）（Ｒ１）` は里々が埋めるので、seq.txt に書かなくてよい
（→ `internals.md`）。

予約の動きを見るときは、`＄次のトーク` を設定するトークを先に喋らせてから
`OnTalk` を送る。

`OnAiTalk` では返らない。`204` になる。

## 1回送っただけでは出ないもの

**送る回数が足りないだけなのに、`204` を見て「動かない」と誤診しやすい。**

なでられは `OnMouseMove` を `＄なでられ反応回数` の回数ぶん受けて、はじめて1回発火する。
座標は見ていないので、動かさずに同じ内容を並べても数は進む。
回数はゴーストが変えられる。固定値を仮定せず、その辞書の設定を見る。
→ `internals.md`

## 確かめられないこと

**テスターで確かめられるのは「里々が正しい文字列を作ったか」まで。**
そこから先は SSP の仕事で、テスターは持っていない。

| | |
|---|---|
| SSP がそのタグを実装しているか | 既存の辞書に無いタグを使ったときは分からない |
| ベースウェアが送る値 | `（Status）` は展開されず文字列のまま残る → `internals.md` |
| 表示の見た目 | バルーンの幅、ウェイトの体感、サーフェスの絵 |
| かかる時間 | 辞書とベースウェアの往復、動きの速さ。**プロパティで取れるのは値であって、時間ではない** |

**テスターの結果だけを見て「この行は要らない」と判断しない。**

## SSP にしか無い情報を取る

バルーンの大きさ、いま表示しているサーフェス、同時に起動している他のゴースト ──
これらを持っているのは SSP である。辞書にもゴーストのファイルにも書かれていない。

SSP が起動中であれば、SSTP を用いて直接取得できる。
`scripts\Get-GhostInfo.ps1` を実行して、プロパティやSHIORIの情報を問い合わせる。

```powershell
# 実行例（バルーンの描画可能幅を取る）
# カレントディレクトリ配下の ghost\master\descript.txt から対象ゴースト名を自動で読み取って実行する。
.\Get-GhostInfo.ps1 -Name "currentghost.balloon.scope(0).validwidth"
```

**まず実行する。**SSP が動いていないか、対象のゴーストが立っていなければ、
ツールがそう言って終わる。動いているかどうかを自分で判別しない。

プロパティ名を誤ると、空が返る。プロパティシステムの仕様を引き、確かめた名前を渡す。

取れなかったら、起動を頼んでよい。
「SSP を起動して、作っているゴーストを立たせてください」と伝える。
**遠慮して仮の値で組まない。**実行時の値でしか決まらないものがある。

頼むかどうかは、その値が無いと決まらないかで判断する。
仮の値で組んで後から直せるなら、頼まずに進めてよい。

バルーンに合わせて並べるときは、必ず取りに行く。
一覧、図鑑、メニュー、表 ── 1行に何個入るかを決める場面がこれにあたる。
仮の値で組む前に、実際の幅を見る。

## 自分で取れないものは、頼む

まず、自分で取れるかを確かめる。取れるものを人にやらせない。

| | |
|---|---|
| プロパティの値 | `Get-GhostInfo.ps1` で取れる。頼まない |
| 辞書が返す文字列 | テスターで取れる。頼まない |
| 機器からの入力 | 取れない。押してもらうしかない |
| 表示の見え方 | 取れない。見てもらうしかない |

取れないものは、遠慮せずに頼む。
頼まないと作れないものがある。
「手間をかけさせない」より、作れないまま終わらせないほうを避ける。

頼むときは、こちらで全部用意する。
確認用の辞書を作り、置く場所と、何をすればよいかを伝える。
**利用者に辞書を書かせない。**

1回で済ませる。必要なものをまとめて聞く。

## 結果の扱い

**5本とも、結果を利用者に見せない。**修正方針を決めるために使う。

検査器は利用者が意図して書いたかどうかを判別できない。
検出したものをそのまま「誤り」として提示しない。
見るのは自分が書いた箇所と、修正を依頼された箇所だけ。

**5本の実行を利用者に頼まない。**書いた側が自分で通す。
頼むのは、[自分で取れないものは、頼む](#自分で取れないものは頼む)に挙げたものだけ。
